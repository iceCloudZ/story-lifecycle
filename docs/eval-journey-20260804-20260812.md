## 0. 背景

**系统**：`story-lifecycle`（D:/github/story-lifecycle）——一套 AI 驱动的研发流程编排系统：TAPD 需求 → 规划 → design（生成 spec）→ code（AI agent 写码）→ verify（质检门禁）→ 交付。核心裁判是 verify 阶段的 LLM judge。

**业务侧**：`hc-all`（D:/hc-all）——菲律宾消费金融微服务平台（Java 11 / Spring Cloud，20+ 仓库），需求管理用 TAPD。

**资源**：OpenCode Go 套餐（约 10B token/月，端点 https://opencode.ai/zen/go/v1，模型 deepseek-v4-flash）。

**两个初始目标**：
1. hc-all 线上预警（定时拉日志/错误/库数据分析）——**至今未兑现，被目标 2 挤占**；
2. 用历史已完成的 TAPD 需求 + 对应代码，让 AI 自动回放，驱动 story-lifecycle 的质量提升——本文档主线。

**协作模式**：kimi 出方案/任务文档/验收（每轮抽查执行方声明后再验收），opencode 执行批量任务。模式定型于多次抓到执行偏差之后（曾因报告归因错误要求返工）。

## 1. 核心纪律（用事故换来的）

写在 `docs/eval-build-handoff.md` §0：

1. **judge 三元组**：端点 + 模型 + prompt 才算 judge 身份。一切评分只认 Go 端点；历史 DeepSeek 官方端点的基线不可直接比较（实测同 case 旧=2 分新=3-5 分）。
2. **pre-flight 端点检查**：批量 LLM 任务放量前必须单条验证实际端点（曾发现 .env 残留导致差点 750 条全量误走 DeepSeek）。
3. **快照冻结**：冻结目录只进不出（两次被打破：全量评分文件误入、severity 回填——均已修复或记录在案）。
4. **删除白名单 + dry-run**：曾有清理脚本 mtime 误判误删 D:/hc-all/story 68 个证据目录（部分不可恢复）；hc-all 默认只读。
5. **human_confirmed 免疫**：人工确认的关联/判定，自动规则不得改判；人工改判留痕（human_recalibrated）。
6. **验收标签与 gate 同一 judge 版本**：judge 升级后标签同源重评，标签迁移不算漏拦/误拦。

## 2. 阶段一：数据地基（8/4-8/6）

**三方匹配**：hc-all 20 个仓库的 2019 个 merge（feature→master 合并）× TAPD 6309 个需求 × 本地证据文件（story/<id>-*/ 下的 spec/PRD）。

- LLM 初配（link-mine：关键词+日期预排序 top15 → LLM 判定）→ 二次无锚定验证（verify-links，397 条）→ 人工分层校准（21 条抽样）。
- 验证发现 LLM 自动关联的错链率 42.8%——单阶段 LLM 关联不可信，双阶段验证必要。
- **日期守卫**：merge 早于需求创建 >90 天 → 确定性 reject；≤90 天 → 时间倒挂待审（先开发后补录需求的真实现象，74 条）。
- 结果：383 条确认关联（个人口径关联率 174/664 ≈ 26%）。

**参照物富化**：285 个「描述只有链接」的 TAPD 需求，通过 webbridge（借浏览器登录态）+ TAPD API 抓取链接正文，212 条成功（story_refs/ 192 文件）。评分参照物优先级：spec > PRD > story_refs > TAPD 描述。富化后同一样本集 alignment 均分 2.64 → 3.43——**参照物质量直接决定评分质量**。

**评分体系**（packages/eval）：
- ConformanceScore：alignment（已实现部分一致性）/ coverage（需求完整度）/ scope_drift（范围漂移）三维 1-5 分 + findings + summary，prompt 经三轮人工校准。
- MergeSummary + DeliveryScore（无关联 merge 用；DeliveryScore 带人名，仅本地不外发）。
- 全量 2019 merge 评分完成：conformance 324 条均分 align 3.51 / cov 2.26 / drift 3.67。

**快照**：
- v1（20260805）：DeepSeek + 旧 prompt，仅存档。
- **v2（20260806，现行标尺）**：Go 端点全量重基 750 键（alignment 均分 3.390）；47 条 replay_samples（21 失败主题 + abcd + gap + construct 6 人造样本）；15 条 held-out（种子 42，密封——迭代期间不调优）；30 个证据目录快照化。

**失败模式挖掘**：94 个 alignment≤2 case 两阶段聚类 → 21 个主题，每主题附改进建议（21 条仅 2 条待人工）。

## 3. 阶段二：考试体系与三轮修复（8/5-8/12）

### 3.1 测试金字塔（packages/eval）

| 层 | 内容 | 关键结果 |
|---|---|---|
| round 1：gate 回测 | 167 条历史 merge 直接喂 verify 门禁 | 拦截 100% / 误拦 71%——后查明是**孤儿组件口径**（见迭代 3） |
| round 2：管线回放 | 20 条 story 沙箱内真实跑 design 阶段 | 完成率 20/20，spec 质量 4.85；暴露 verify LLM 超时 fallback approve 等 4 个缺陷 |
| round 2.5：覆盖率 | 代码路径/场景/决策分支/缺陷模式四维 | 决策分支 gate fail/swap/rescue 未触发；缺陷模式 21 主题无用例 |

### 3.2 迭代 1（commit d34310fc→2b4db820）：fail-closed + conformance 质检器

- F1：judge LLM 失败时 fallback 从 approve（静默放行）改 escalate（转人）+ 瞬态重试 ×2。
- F2：conformance 质检器移植进核心包，verify 阶段现场打分，**双阈值**：align≤2 或 cov≤2 → HIGH finding 注入判决。
- 验收中发现 judge 口径漂移（同 case 新旧 prompt 分差），确立三元组纪律与「标签同源重评」原则。

### 3.3 迭代 2（commit 1555e08f）：UI 修复

- 主流程死锁：前端三处 `status==='planning'` 恒假（状态机四态无 planning）→ 后端显式 planConfirmed 字段。
- QualityPanel：gate 历史/findings/repair_action 可见（后查明只修了一半，见迭代 3）。
- judge 误判「产出为空」：产物路径解析加 glob + PATH-MISS 守卫（找不到 → escalate 转人，写得差 → reject 返工，分开处理）。

### 3.4 迭代 3（commit 64f189e7）：裁判统一——全程最重要的发现

**代码考古发现系统里有两个 verify 裁判**：
- `judge_stage_completion`：生产真实裁判（scheduler 实际调用），迭代 1 的 F2 接在这里；
- `run_unified_verify_gate`：**生产零调用方的孤儿**（函数级孤儿；模块内两个工具函数被生产裁判 import——opencode 探明阶段按纪律停下报告，避免了直接删除导致的静默降级）。

**此前所有 gate 回测（167+47+15 条）测的都是孤儿**——拦截率 84%、held-out 9/9 等数字不代表线上行为。迭代 1/2 对孤儿的维护全是白费。

处置：回放改测生产裁判（conformance 现场算，走生产输入通道）；工具函数迁移后删除两个孤儿模块（-1349 行）；评分落盘 severity 化（750+2019 离线回补，零 LLM）；生产裁判的 findings/repair_action 落库（QualityPanel 在生产真正可见——迭代 2 只修了一半）。

**重测结果**：62/62 完成，应拦 36/36 全拦。但 4 条争议样本（应放）仍全拦——拦因是**沙箱缺执行轨迹/test_report，judge 证据不足只能保守**，非 judge 对 medium 敏感。结论：沙箱测得出拦截能力，测不出放行准确率。

**孤儿普查**还发现：boundary_judge.py（第二个孤儿，docstring 声称 unified_gate 并入它，结果两者皆孤儿）、nodes/ 空壳 + demo.py 坏引用、round 2.5「graph.py 死代码」系误报（graph.py 是 CLI/API 活入口）。

### 3.5 迭代 4（进行中）：ABC 三线

- **A 线（三格对照）**：给沙箱补模拟证据（session/事件流/test_report 中性模板），格 1 合格 15 条+全证据→期望放行；格 2 应拦 19 条+同样全证据→期望仍拦（测裁判听内容还是听证据有无）；格 3 复用迭代 3。**决策规则预注册**（跑前定死四种结果组合各自的结论与后续动作）。dry-run 信号：拦因已从「证据不足」转向「conformance 内容」；LLM 能识别模板 test_report 打折扣（预判风险实锤）。
- **B 线（50 条真实回放放量）**：历史 story 沙箱内真实执行（design→code→verify），agent 真实跑，数小时级；选样 10+19+21 三层、与全部历史样本零重叠（已独立核验）；gate 判决在 A 出结论前只记录不解读。常驻化：每晚 5 条 + 日预算 10 条 + 断点续跑——10B token 的长期消费器。
- **C 线（已完成，commit ff013852）**：`story judge-feedback` CLI + judge_feedback 表 + `eval human-matrix` 月报——真实使用中人判 vs 机判的混淆矩阵，零 LLM 成本。

## 4. 关键认知（按获得顺序）

1. 单阶段 LLM 关联不可信（42.8% 错链率）→ 双阶段验证 + 人工校准 + 日期守卫。
2. 参照物质量决定评分质量（富化后 Δ+0.79）；「描述只有链接」的需求必须抓正文。
3. judge 三元组变更 = 基线作废（端点/模型/prompt 任一变化，历史分数不可比）。
4. **回测对象必须是生产路径上的组件**——考了三周才发现考的是孤儿裁判；F2 上线后生产裁判从未被端到端验证，迭代 3 才补上。
5. 回放保真度限制：沙箱缺执行证据时 judge 系统性保守——拦截率可信，放行率不可信。
6. 双阈值（align≤2 或 cov≤2）实战价值：held-out 中 6 条「高分低覆盖」靠 coverage 腿正确拦截，align-only 口径会漏。
7. 门禁判定依据（findings 文本语义）与评分标签（数值）是两套度量，固有张力需显式管理（severity 化贯通解决）。
