### 问题 #2 — intake/preview 偶发 500:PRD generator LLM 输出非合法 JSON

**严重度**:高(用户首个动作就可能撞上)
**类型**:bug

**现象**:POST /api/intake/preview 第一次调用 500,serve 日志抛 `ValueError: Cannot parse LLM response as JSON after 2 attempts`。LLM(deepseek)把「思考过程」当正文输出,首字符不是 `{`。第二次重试成功(103s)。

**根因**(读码确认,3 层叠加):
- `infra/llm_client.py` `_build_body` 从不设置 `response_format={"type":"json_object"}`——deepseek 的 OpenAI 兼容 API 支持 JSON 模式,可从 API 层保证输出是合法 JSON,这里没用
- `invoke_structured` 的纠正 nudge(`llm_client.py:315-328`)把上一次坏输出**原文回灌**(`上次返回（错误示范，不要这样）：{last_content[:800]}`)——实测诱导模型继续元讨论(重试输出开头就是「用户说上一次回答不是合法 JSON,要求重新…」),纠正适得其反
- 解析层(`_parse_json`:direct → fence → `_extract_json_object` 括号计数)已足够健壮;失败是因为模型输出**纯思考散文、全文无完整 JSON 对象**,解析层无能为力
- 诱因:需求正文核心在不可访问的图片里,模型在 needs_clarification vs manual_download_required 之间纠结,把纠结过程当正文输出

**代码引用**:
- `packages/story-lifecycle/src/story_lifecycle/infra/llm_client.py:346`(raise)
- `packages/story-lifecycle/src/story_lifecycle/infra/llm_client.py:315-328`(correction 回灌)
- `packages/story-lifecycle/src/story_lifecycle/infra/llm_client.py` `_build_body`(无 response_format)

**修复方向**:a) `invoke_structured` 的请求体加 `response_format={"type":"json_object"}`(对 deepseek/openai 兼容源生效,不支持的源需探测降级);b) 纠正 nudge 去掉坏输出原文回灌,只保留指令;c) 二次尝试可提高 max_parse_retries。

**状态**:未修

### 问题 #7 — 无项目绑定的沙箱 story:agent 自建 worktree 不被登记 → build git 成果物永不落地

**根因**:
- 沙箱 prompt(prompts.py「工作沙箱」段)只教 agent 建 worktree,没教它登记(`PUT /api/story/{key}/context/branch`,该端点注释明说「agent-driven flows that prepare the branch themselves」就是为此设计)
- 对照:1068018(完成)在 /start 时选了项目 → intake.py:85 绑定 + worktree_path 落库 → 检测正常。断点只在「无绑定」路径

**代码引用**:
- `orchestrator/engine/artifact_check.py:220-223`(git 检查只看 ws + 注册的 git_worktrees)
- `orchestrator/executors.py:157-166`(git_worktrees 来源=story_project.worktree_path)
- `orchestrator/prompts.py` 沙箱段(无登记指引)

**副作用**:登记后 git 一有改动 judge 即触发——本例 agent 还在写码就被评了(reject #1 打在半成品上)。「git 有改动」≠「干完了」,完成信号语义弱。

**修复方向**:a) 沙箱 prompt 补「建完 worktree 立即 PUT context/branch 登记(worktree_state=available)」;b) 编排侧兜底:tick 时扫描沙箱目录一级子目录是否为 git 仓库且有改动(自动发现,不依赖 agent 登记);c) git 完成语义改进(如要求 PTY idle + 有改动,或 agent 显式 declare)。

### 问题 #6 — `story tool declare --content "$(cat …)"` 命令行参数溢出

**严重度**:中
**类型**:bug(CLI 健壮性)

**现象**:build/design agent 用 `story tool declare spec story/spec.md --content "$(cat spec-v3.md)"` declare 31KB 文档,Git Bash 报 `/usr/bin/bash: line 1: …/Scripts/story: Argument list too long`(argv 上限约 32KB)。agent 换了方式重试成功(事件里 v3 declare 落了),但这个失败模式必然复现——大文档走 --content 必炸。

**根因**:declare 子命令支持 `--content` 内联正文,agent(prompt 指引)倾向 `--content "$(cat file)"`;正文应从 path 参数直接读文件,不走 argv。

**代码引用**:
- `story tool declare` CLI 入口(entry 层,`--content` 参数处理)
- 规划/执行 prompt 中 declare 用法指引

**修复方向**:a) declare 检测 `--content` 超长(>8KB)报错并提示「直接 declare 路径」;b) 支持 stdin(`cat x.md | story tool declare spec story/spec.md`);c) prompt 指引改为 declare 路径优先。

**状态**:未修(agent 自行绕过)
