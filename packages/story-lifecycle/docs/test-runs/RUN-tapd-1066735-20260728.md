## 发现清单

### 问题 #1 — kill_pty / emergency-stop 不清 story_session 悬空记录,导致 resume 死 sid 崩

**严重度**:高
**类型**:bug

**现象**:
story 被 emergency-stop(或任何 kill_pty 路径)停止后,用同一个 (story, stage, adapter) 重新 spawn 必崩。claude 启动后立刻报 `No conversation found with session ID: <uuid>` 秒退,30 秒后 planner 判定 "PTY exited without landing artifacts" 标 failed。

**根因**:
- `kill_pty` 只清内存 PTY 注册表(`_ptys`)+ kill 进程,**不清 DB `story_session` 表**。
- spawn 路径(`planner.py:1126-1138`)的 resume 判定:`_prior = get_session(...)`;`if _prior and _prior.get("session_id")` → 走 resume 传 `session_id` 给 `claude --resume`。
- `compute_session_id` 是确定性 uuid5(`models.py:2452`),被杀的会话和重新 spawn 算出**同一个 sid**。
- 于是 spawn 拿被杀会话的 sid 去 `--resume` → claude 本地找不到该会话 → "No conversation found" 秒退。
- 违反 AGENTS.md driver 不变式「CLI 生命周期 ⊆ driver 生命周期」——杀掉的进程状态没回收。

**代码引用**:
- `infra/terminal/pty.py:613` — `kill_pty` 原本只清内存 + kill,不碰 DB
- `infra/db/models.py:2455` — `get_session` 是 resume 判定的数据源,session_id 非空就 resume
- `orchestrator/engine/planner.py:1126-1138` — spawn 的 resume 决策分支
- `infra/db/models.py:2436` — `compute_session_id` 确定性 uuid5(同三元组永远同 sid)

**修复方向**:
- `kill_pty` 杀进程后同步清 DB `story_session` 记录:指定 session_id 清单条三元组,不指定清整 story(兜底覆盖只 upsert DB 没 spawn PTY 的 adapter)。
- 新增 `db.delete_session(story_key, stage, adapter)` / `delete_session(story_key)` 两种签名,对齐 kill_pty 的「单 sid / 全 story」语义。
- DB 清理 best-effort(try/except),不阻塞 kill 本身。

**状态**:已修(本次改动,待 commit)

**类型**:bug
